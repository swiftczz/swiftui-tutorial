# 01 声明式 UI：换一种想法写界面

## 本章目标

- 说清楚“命令式”和“声明式”写界面的区别，以及后者解决了什么问题
- 理解 `UI = f(State)` 这个公式里每个部分指什么
- 知道 SwiftUI 的视图是“描述”而不是“屏幕上的东西”
- 对一次界面更新的完整流程有一个大致的图景

## 从一个计数器说起

假设要做一个最简单的界面：一个数字，一个“加一”按钮，数字到 10 的时候变红，并且按钮变成不可点。

先别想 SwiftUI。如果让你用最朴素的办法做，你大概会这样想：

1. 创建一个标签，显示 `0`
2. 创建一个按钮，标题是“加一”
3. 按钮被点击时：把数字加一；把标签的文字改成新数字；如果数字到了 10，把标签颜色改成红色，把按钮设为禁用

用伪代码写出来是这样（这不是 SwiftUI，只是为了说明思路）：

```swift nocheck
// 命令式写法（伪代码）
var count = 0
let label = Label(text: "0")
let button = Button(title: "加一")

button.onTap = {
    count += 1
    label.text = "\(count)"          // 手动同步文字
    if count >= 10 {
        label.color = .red           // 手动同步颜色
        button.isEnabled = false     // 手动同步可用状态
    }
}
```

这叫**命令式**（imperative）写法：你告诉计算机每一步该**做什么**。它很直观，但请注意一件事：`count` 是真正的数据，而 `label.text`、`label.color`、`button.isEnabled` 是这份数据在界面上的三个“副本”。每次数据变了，**你**要负责把每个副本都改对。

::: info 想一想
现在加一个需求：再加一个“重置”按钮，点了之后数字回到 0。上面的代码要改几处？如果你忘了把颜色改回黑色、忘了把“加一”按钮重新启用，会发生什么？
:::

答案是：界面会停在一个“数字是 0，但颜色是红的，按钮还点不了”的状态。数据是对的，界面是错的。这类 bug 有个名字，叫**状态不同步**。界面越复杂，数据和它的副本之间要维护的同步关系就越多，漏掉一条就是一个 bug。命令式 UI 里的大部分疑难杂症，归根结底都是这一种。

## 换一种想法

声明式（declarative）的思路是把问题反过来。不描述“数据变了以后要改哪些地方”，而是描述“**数据是这样的时候，界面应该长什么样**”：

- 标签的文字是 `count`
- 标签的颜色：`count >= 10` 时是红色，否则是默认色
- 按钮是否禁用：`count >= 10`

写成 SwiftUI：

```swift
struct CounterView: View {
    @State private var count = 0

    var body: some View {
        VStack(spacing: 16) {
            Text("\(count)")
                .font(.largeTitle)
                .foregroundStyle(count >= 10 ? .red : .primary)

            Button("加一") {
                count += 1
            }
            .disabled(count >= 10)

            Button("重置") {
                count = 0
            }
        }
        .padding()
    }
}
```

把它粘进 Xcode，加一个 `#Preview { CounterView() }` 运行看看。然后对照着读代码：

- 按钮的动作里只有 `count += 1` 和 `count = 0`。**没有任何一行代码去改标签的文字、颜色或按钮的可用状态。**
- “重置”功能只加了一个按钮、一行赋值。颜色自动变回去了，“加一”自动可点了。

我们没有写“同步”的代码，因为根本没有副本需要同步。`body` 描述了界面和 `count` 之间的关系，`count` 一变，SwiftUI 重新计算 `body`，得到新的描述，再把屏幕更新成新的样子。

## UI = f(State)

这个思想可以浓缩成一个公式：

```text
UI = f(State)
```

- **State** 是数据，这里是 `count`。它是唯一的事实来源（source of truth）。
- **f** 是 `body`，一个从数据计算出界面描述的函数。
- **UI** 是 `body` 的返回值，一份对界面的描述。

这个公式有两个推论，它们会贯穿整个教程：

**推论一：同样的状态，一定得到同样的界面。** 界面不会“记住”它以前是什么样子。不存在“先变红了，后来没改回来”这种事，因为每次都是从状态重新算出来的。于是调试界面问题变成了一个简单的问题：此刻的状态是什么？

**推论二：想改界面，只有一个办法，就是改状态。** 你不能“拿到那个标签，把它的文字改掉”。SwiftUI 里根本没有“拿到那个标签”的途径。这在一开始会让人不习惯，但它正是不会出现状态不同步的原因。

::: tip 换脑子的诀窍
每当你想问“我怎么把这个视图改成……”，就把问题改写成：“**哪个状态**决定了它现在的样子？我该怎么改那个状态？” 如果答案是“还没有这样一个状态”，那就加一个。
:::

## 视图是描述，不是实物

上面说 `body` 返回“一份对界面的描述”，这句话值得停下来体会。

在很多传统 UI 框架里，一个视图是一个**对象**：它被创建出来，一直存在，占用内存，持有自己的子视图，你可以改它的属性。在 SwiftUI 里，`Text("\(count)")` 不是屏幕上的那段文字，它只是一个很轻的结构体，内容大致是“这里要有一段文字，内容是这个字符串”。

可以用餐厅来类比。`body` 是你写的点菜单，SwiftUI 是后厨。你每次状态变化都重新写一张完整的点菜单交过去，后厨拿新单子和旧单子比较，只重做变了的那几道菜。你从不进后厨，也不碰盘子。

这带来几个很实际的结论：

1. **创建视图非常便宜。** `Text`、`VStack`、你自己写的 `CounterView`，都只是结构体的值。SwiftUI 可以每秒重新创建它们很多次，你不用为此担心性能。所以不要怕把大视图拆成很多小视图。
2. **`body` 会被调用很多次，而且调用时机不由你决定。** 所以 `body` 里只应该做一件事：根据当前状态返回描述。不要在里面发网络请求、写文件、改状态。
3. **视图结构体本身不保存任何需要长期存活的东西。** 你也许注意到了一个矛盾：`CounterView` 是结构体，结构体每次都重新创建，那 `count` 是怎么“活下来”的？答案在 `@State` 上：它告诉 SwiftUI“这份数据请你替我保管”，真正的存储在 SwiftUI 内部，不在结构体里。第 3 章和第 9 章会把这件事讲透。

## 一次更新的全过程

把上面的内容串起来，点一下“加一”按钮之后发生了什么：

```text
① 用户点击按钮
      ↓
② 按钮的动作闭包执行：count += 1
      ↓
③ SwiftUI 发现 count 变了，把读取过 count 的视图标记为“需要更新”
      ↓
④ SwiftUI 重新调用这些视图的 body，得到新的描述
      ↓
⑤ 对比新旧描述，找出差异（文字 "3" → "4"）
      ↓
⑥ 只把有差异的部分更新到屏幕上
```

你写的代码只参与第 ② 步和第 ④ 步。其余的都是框架的工作。

注意第 ③ 步里的“读取过 `count` 的视图”：SwiftUI 知道哪些视图依赖哪些状态，所以只会重新计算真正受影响的视图，不会把整个界面重算一遍。依赖关系是自动建立的，你在 `body` 里读了某个状态，就等于登记了“我依赖它”。

## 声明式不是没有代价

学一样东西也要知道它的边界。声明式 UI 的代价主要有两点：

- **控制权让渡给了框架。** 何时调用 `body`、如何对比差异、动画怎么插值，都由 SwiftUI 决定。大多数时候这是好事，但当行为不符合预期时，你得理解框架的规则才能解释它。这也是这门教程花大量篇幅讲原理的原因。
- **有些事情天然是命令式的。** “滚动到第 20 行”“让输入框获得焦点”“播放一段动画”，这些是动作，不是状态。SwiftUI 的做法是把它们也表达成状态（滚动位置、焦点、动画阶段），后面的章节会逐个讲到。

## 常见误区

**误区一：“声明式就是不用写逻辑。”** 逻辑一点没少，只是换了位置。命令式把逻辑写在“事件发生时该改什么”，声明式把逻辑写在“状态和界面是什么关系”。`count >= 10 ? .red : .primary` 就是逻辑。

**误区二：“每次都重建整个界面，一定很慢。”** 重建的是轻量的描述，不是屏幕上的像素。真正昂贵的渲染只发生在有差异的部分。

**误区三：“我可以在 `body` 里顺手做点别的。”** 不可以。`body` 必须是一个只依赖状态的纯计算。副作用有专门的位置，比如按钮的动作闭包、`.task`、`.onChange`，后面会学到。

## 小结

- 命令式 UI 的核心难题是数据和界面之间的手动同步，漏掉同步就产生 bug。
- 声明式 UI 用 `UI = f(State)` 消除了同步问题：界面永远从状态重新算出来。
- SwiftUI 的视图是轻量的值类型描述，创建成本极低，`body` 会被反复调用。
- 改界面的唯一方式是改状态。
- SwiftUI 自动追踪视图对状态的依赖，只更新受影响的部分。

## 练习

1. 给 `CounterView` 加一个“减一”按钮，要求数字为 0 时“减一”不可点。写完后数一数：为了这个需求，你写了几行“同步界面”的代码？
2. 在数字下面加一行说明文字：小于 5 显示“还早”，5 到 9 显示“快到了”，等于 10 显示“满了”。先想清楚这行文字**依赖哪个状态**，再动手。
3. 不看代码，用自己的话向别人解释：为什么 SwiftUI 里没有“获取某个标签并修改它的文字”这样的 API？
